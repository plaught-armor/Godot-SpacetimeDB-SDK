# SpacetimeDB Bindings Generation

## Prerequisites

-   You have the [SpacetimeDB SDK addon](installation.md) installed in your Godot project
-   A SpacetimeDB module published to a SpacetimeDB server
    _The codegen tool uses the SpacetimeDB API to generate all types and reducers_

## Generate module bindings

1. Open the SpacetimeDB tab in the bottom dock
2. Replace the default URL with your server's URL
   ![](images/codegen-server-uri.png)
3. Click "Check URI" to verify the addon can reach your server
4. Enter your module name (and optionally an alias) and click the `+` button
   ![](images/codegen-add-module.png)
   - **Module alias** (optional): A custom name for the module client. Defaults to the module name.
   - **Hide scheduled reducers**: Hides auto-generated scheduled reducers from the bindings.
   - **Hide private tables**: Hides private tables from the bindings.
5. You can now click the `Generate schema` button to generate the bindings, all generated code is placed in `res://spacetime_bindings/`

## Headless regeneration (CI / scripts)

Once at least one module is configured in the editor (the config is saved to
`res://addons/SpacetimeDB/plugin_config.tres`), you can regenerate bindings
without opening the editor — useful for CI or a pre-build step:

```sh
godot --headless --path <project> --import   # once per checkout, see below
godot --headless --path <project> --script res://addons/SpacetimeDB/cli.gd
```

It loads the saved plugin config, fetches each configured module's schema from
the server, regenerates `res://spacetime_bindings/`, and exits `0` on success or
`1` on failure (config missing, no modules configured, or codegen error). The
server URL and module list come from the saved config — configure them in the
editor UI first.

**Import once on a fresh checkout.** Godot resolves `class_name` identifiers through
`.godot/global_script_class_cache.cfg`, which only an import or an editor session
writes — and Godot's project `.gitignore` keeps `.godot/` out of the repository. So on
a CI clone the addon's classes do not resolve yet, and a `--script` run does not write
the cache either, no matter how many times you run it. Run `--import` first (or cache
`.godot/` between CI runs); without it, the codegen run refuses with the same advice.

Two more things worth knowing for CI: commit `res://addons/SpacetimeDB/plugin_config.tres`
so the runner has the server URL and module list, and note that the generated autoload is
registered in `project.godot` by the **editor** — commit that entry too, since a headless
run cannot add it.

## Generated bindings structure

The generated bindings are placed in `res://spacetime_bindings/` and are structured as follows:

-   `codegen_debug/` contains the parsed SpacetimeDB schema for debugging purposes, you can delete this folder if you want.
-   `schema/` contains all of the generated bindings for your SpacetimeDB module.
    -   `schema/spacetime_autoload.gd` is the autoload singleton that instantiates all module clients. Registered as the `SpacetimeDB` autoload.
    -   `schema/types/` and `schema/module_*_types.gd` contains all of your SpacetimeDB types, table structs and enums, used by the BSATN deserializer.
    -   `schema/tables/` and `schema/module_*_db.gd` contains a representation of your module's tables allowing you to easily query the local database. This includes unique index files (`*_unique_index.gd`) for typed lookups on unique columns and btree index files (`*_btree_index.gd`) for `filter` / range lookups on non-unique indexed columns.
    -   `schema/module_*_reducers.gd` contains all of the reducer functions for your module.
    -   `schema/module_*_procedures.gd` contains all of the procedure functions for your module, each returning a [`SpacetimeDBProcedureCall`](api.md#spacetimedbprocedurecall-class) handle.
    -   `schema/module_*_client.gd` is the SpacetimeDB client for your module which handles the SpacetimeDB connection and exposes the database, reducers, and procedures.

The saved plugin configuration lives outside the generated tree, at `res://addons/SpacetimeDB/plugin_config.tres` — it holds the plugin UI and codegen settings. Do not edit this file directly.

## Namespaced submodules

A module can register another module under a namespace (SpacetimeDB 2.8.1+, authored
today only by the TypeScript server SDK). The server registers a submodule's tables and
reducers under a dotted name — `lib.lib_data`, `auth.baz.baz_items` — and namespaces
nest, so a name can carry more than one dot.

A dot cannot appear in a GDScript identifier, so each generated name carries the
namespace as a prefix while the wire name keeps its dots:

| Def | Wire name | Generated |
| --- | --- | --- |
| root table `root_thing` | `root_thing` | `db.root_thing`, `MyModRootThing` |
| `lib`'s table `lib_data` | `lib.lib_data` | `db.lib.lib_data`, `MyModLibLibData` |
| `auth.baz`'s table `baz_items` | `auth.baz.baz_items` | `db.auth.baz.baz_items`, `MyModAuthBazBazItems` |
| `lib`'s reducer `lib_insert` | `lib.lib_insert` | `reducers.lib.lib_insert(...)` |

```gdscript
var row: MyModLibLibData = SpacetimeDB.MyMod.db.lib.lib_data.first_by_id(7)
await SpacetimeDB.MyMod.reducers.auth.baz.baz_insert(3).wait_for_response()
SpacetimeDB.MyMod.subscribe(["SELECT * FROM lib.lib_data"])
```

Each namespace becomes an inner class on the db, reducers and procedures facades, so
`db.lib` and `reducers.lib` are typed and autocomplete like any other generated member.
Subscription SQL and `SpacetimeDBQuery.table(...)` take the **wire** name, dots included —
that is what the server's SQL parser and its reducer dispatch answer to.

Two things to know about what is generated:

-   **Each submodule has its own typespace.** A type declared in a submodule becomes its
    own GDScript class (`MyModLibLibPoint`), distinct from a same-named type in the root
    module, and rows bind to the one their own module declared.
-   **Private tables and non-public functions follow the same filters as the root
    module's** — a private submodule table is omitted when the module's
    *Hide private tables* option is on (the default).

Two sibling namespaces whose names differ only in case or separators
(`my_auth` and `myAuth`) would generate one class name for both; codegen refuses the run
and names them rather than emitting a file Godot cannot parse.

## Reserved and colliding names

A name that is legal in your module can be illegal as a GDScript member. Godot refuses
to load a script whose method overrides a native one (`Object.set`, `Object.get_class`)
or whose variable redefines an inherited property (`Resource.script`,
`Resource.resource_name`), and one such name makes the **whole binding** unusable —
every other table and reducer in the module goes down with it.

The codegen renames those names by appending a single underscore, so the binding always
loads:

| Module name | Generated GDScript | Collides with |
| --- | --- | --- |
| reducer `set` | `func set_(...)` | `Object.set()` |
| procedure `notification` | `func notification_(...)` | `Object.notification()` |
| enum variant `class` | `func get_class_()` | `Object.get_class()` |
| column `script` | `@export var script_` | `Object.script` |
| column `resource_name` | `@export var resource_name_` | `Resource.resource_name` |
| column / index `count` | `var count_` | `_ModuleTable.count()` |
| column `create` | `@export var create_` | the row type's own `create()` |
| table `script` | `var script_` on the db facade | `Object.script` |

Three name sets are checked: what the engine base class already defines (asked of
`ClassDB` and a probe instance, so it stays correct across engine versions), what the
SDK's own base classes define (`_ModuleTable`, `_ModuleTableType` — `count`, `iter`,
`find_by`, the row callbacks), and what the codegen itself emits (`create`,
`BSATN_TYPES`, `PRIMARY_KEY`, `module_name`, `table_names`, the typed change signals).
GDScript reserved words (`match`, `var`, `class`) are escaped the same way.

Two things worth knowing:

-   **The wire name never changes.** A reducer renamed to `set_` still sends `set`, and a
    column renamed to `script_` still decodes the `script` column — only the GDScript
    surface is renamed. Nothing about your module needs to change.
-   **The rename is applied consistently.** A column's escaped spelling is used by the row
    property, its `BSATN_TYPES` entry, the `create()` parameter, and any index that
    resolves the property by name — so index lookups keep working.

If you would rather not see the underscore, rename the column or reducer in your module.

### When two names escape to the same identifier

The escapes above guarantee the name they produce is free on the *base class*, but they
cannot see a *sibling* that escaped to the same string. A module with a reducer `set`
(escaped to `set_`) **and** a reducer literally named `set_` produces `func set_()`
twice, and Godot refuses to load the whole script:

```
Parse Error: Function "set_" has the same name as a previously declared function.
```

Codegen now detects this and fails the run with the file and the identifier, instead of
letting you find out at load time from a message that names neither of the two module
names involved. The fix is to rename one of them in your module — codegen deliberately
does not pick a winner for you, since which of the two ends up with the mangled spelling
is your call. The same applies to a column pair like `count` / `count_` and a table pair
like `table_names` / `table_names_`.

## Enum deduplication

When generating bindings, the codegen automatically scans your project for existing GDScript enums that match enums defined in your SpacetimeDB module. If an enum with the same name and matching variants is found, the codegen will use your project's enum instead of generating a duplicate.

The scan checks:

-   **Global classes** — any script with a `class_name` declaration
-   **Autoloads** — singletons registered in Project Settings, including those using `uid://` paths

### How matching works

1. The codegen compares enum names (PascalCase) between your module schema and project scripts.
2. If a name matches, it compares variants using `to_snake_case()` normalization — so `LeftArm` (PascalCase from the server) matches `LEFT_ARM` (SCREAMING_SNAKE_CASE in your project).
3. If all variants match, the generated types will reference your project's enum directly.
4. If variants differ, the codegen falls back to generating a standalone enum and logs a warning.

### Example

Given a server enum `BodyRegion { Head, Torso, LeftArm, RightArm, LeftLeg, RightLeg }` and a project autoload:

```gdscript
# scripts/autoloads/globals.gd
extends Node

enum BodyRegion {
    HEAD = 0,
    TORSO = 1,
    LEFT_ARM = 2,
    RIGHT_ARM = 3,
    LEFT_LEG = 4,
    RIGHT_LEG = 5,
}
```

The generated type will use your existing enum:

```gdscript
# Generated: world_body_condition_row.gd
@export var Region: Globals.BodyRegion
```

Instead of generating a duplicate `WorldTypes.BodyRegion`.

### Requirements

-   Variant names must match after `to_snake_case()` normalization.
-   Variant count must be identical — extra or missing variants will prevent matching.
-   The enum must be declared in a script that is either a global class (`class_name`) or a registered autoload.
