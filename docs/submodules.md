# Submodules / namespaces

**Status: supported.** A module that registers other modules under namespaces
(SpacetimeDB 2.8.1+, PR [#5486](https://github.com/clockworklabs/SpacetimeDB/pull/5486))
generates bindings for every submodule's tables, reducers, procedures and views.

Only the TypeScript server SDK can author them today — verified against `v2.8.3`:
`crates/bindings-typescript` implements them, the C++ and C# bindings carry only the
autogenerated `RawSubmoduleV10` type mirror, and the Rust bindings have no submodule
surface at all. So a module a Godot client talks to can only use namespaces if it is a
TypeScript module.

The rest of this note records what the feature does to the wire and how that maps onto
the generated bindings. For the user-facing shape of the generated names, see
[Namespaced submodules](codegen.md#namespaced-submodules) in the codegen guide.

## What the wire looks like

Everything below was verified against a live 2.8.3 server running
[`integration-tests/verify_submodule_module`](../integration-tests/verify_submodule_module),
whose captured `/v1/database/<db>/schema?version=10` response is committed as
`godot-client/tests/fixtures/vsubmod.json`.

A recapture will not be byte-identical to that fixture even on an unchanged server:
the entries of every `Types` section — root and each submodule's — come back in an
unstable order. `ModuleDef.types` is a `HashMap<ScopedTypeName, TypeDef>`
(`crates/schema/src/def.rs`), and `RawModuleDefV10::from` emits it with
`types.into_values()`, so the section carries Rust's per-process hash seed. Measured:
stable within one server process (three republishes of `vsubmod` gave one order, and
two fetches agree), different on each restart (three restarts, three orders). Sibling
sections do not move — `reducers`, `procedures` and `views` are `IndexMap` upstream
precisely because their order is load-bearing for `__call_reducer__` and friends.

None of that reaches the bindings: the parser sorts `Types` by `ty` and the table,
reducer and procedure lists by name for exactly this reason (`schema_parser.gd`, see
the comment at `_parse_schema`'s tail). Measured on this fixture's module —
regenerating `vsubmod` under two different `Types` orders produced byte-identical
`.gd` output, namespace facades included; only the gitignored
`codegen_debug/unparsed_schema_*.json` dump moved. So compare a recapture
order-insensitively before reading a diff as a regression. The 2.8.3 recapture was
equal to the committed 2.8.2 capture under that comparison, so the committed bytes
were kept.

**A schema section carrying a whole nested module.** `RawModuleDefV10Section` has a
`Submodules(Vec<RawSubmoduleV10>)` variant, where each entry is
`{ "namespace": "lib", "module": { "sections": [...] } }` — a complete
`RawModuleDefV10`, with its own `Typespace`, `Types`, `Tables`, `Reducers` and
`ExplicitNames`. Submodule tables are **not** flattened into the root `Tables` section.

**Each nested module has its own type-ref space.** In the captured fixture the root
`Typespace` and the `lib` `Typespace` both have a type at index `0`, and they are
different types. `product_type_ref: 0` inside the submodule means "index 0 of the
submodule's typespace". A parser that hoisted submodule tables into the root table list
without also scoping their type refs would silently bind rows to the wrong type — this is
the single biggest hazard in the format, and the reason
`godot-client/tests/test_submodule_schema.gd` asserts on the resolved column type rather
than on the generated text alone.

**Names on the wire are dot-qualified, using the canonical spelling.** The engine
registers a submodule table under `<namespace>.<canonical_name>` and a reducer under
`<namespace>.<canonical_name>`:

| Def | `source_name` | `ExplicitNames` canonical | Wire / catalog name |
| --- | --- | --- | --- |
| root table | `rootThing` | `root_thing` | `root_thing` |
| submodule table | `libData` | `lib_data` | `lib.lib_data` |
| root reducer | `rootInsert` | `root_insert` | `root_insert` |
| submodule reducer | `libInsert` | `lib_insert` | `lib.lib_insert` |

The accessor spelling is an alias, never an identity — `lib.LibData` is explicitly
rejected (`crates/schema/src/schema.rs`, `check_compatible_submodule_table_name`).
Namespaces nest, so a name can carry more than one dot (`auth.baz.baz_items`), and the
SQL parser joins all leading parts back into one catalog name rather than treating them
as qualification (`crates/sql-parser/src/parser/mod.rs`, `parse_parts`). Subscriptions
therefore read `SELECT * FROM lib.lib_data`, and `CallReducer` carries `lib.lib_insert`.

**Nothing else about the protocol changed.** `crates/client-api-messages` is
byte-identical from `v2.7.0` through `v2.8.3`.

## How the SDK maps it

- **Parser** (`addons/SpacetimeDB/codegen/schema_parser.gd`) flattens the module tree
  depth-first, root first, and concatenates every module's typespace into the one list
  the rest of the parse indexes. Each submodule's `Ref`s are rewritten by the offset its
  types landed at — every `Ref` in the module's sections, not only the ones in its
  `Typespace`, because a reducer's parameters and a view's return type carry them too.
  `ExplicitNames`, `Schedules`, `LifeCycleReducers` and `ViewPrimaryKeys` are read per
  module, since a source name is unique only within the module that declared it.
- **Two names per def.** Every table, reducer, procedure and view carries the dotted
  `wire_name` the server answers to and an identifier built from the namespace
  (`lib.lib_data` → `lib_lib_data`) for its class, file and member names. Type names take
  the namespace in PascalCase (`LibPoint` in `lib` → `LibLibPoint`), except names the SDK
  maps to an engine type (`Vector3`, `Color`, the `__identity__` family), which are
  matched by name and left alone.
- **Codegen** emits one inner class per namespace on the db, reducers and procedures
  facades, nested as the modules are (`db.auth.baz.baz_items`). Two sibling namespaces
  that would generate one class name fail the run rather than emitting a file Godot
  cannot parse.
- **Visibility** follows the module's existing filters: a private submodule table is
  omitted when *Hide private tables* is on, exactly as a private root table is.

## Verifying against a real module

`integration-tests/verify_submodule_module` is a TypeScript module with a `lib`
namespace, an `auth` namespace nesting a `baz` namespace inside it, a private submodule
table, and a same-index/different-shape type in each module. Publish it and run the
harness — it subscribes by dotted name, calls a submodule and a nested-submodule reducer,
and reads the rows back through the namespace facades:

```sh
spacetime start &
npm install --prefix integration-tests/verify_submodule_module
spacetime publish -p integration-tests/verify_submodule_module \
    -s http://127.0.0.1:3000 vsubmod --yes
# Point addons/SpacetimeDB/plugin_config.tres at the `vsubmod` module, then:
cd godot-client && <godot> --headless --path . --script addons/SpacetimeDB/cli.gd
cp ../integration-tests/verify_live_submodule.gd .
<godot> --headless --path . --script verify_live_submodule.gd   # ALL PASS (8/8)
```

To re-capture the fixture after an upstream format change, fetch the schema from the
running server (`curl "http://127.0.0.1:3000/v1/database/vsubmod/schema?version=10"`) and
regenerate the goldens. [`integration-tests/schema_probe/`](../integration-tests/schema_probe)
still exists for shapes that cannot be published at all — it runs the schema route's own
conversion offline — but a published module is the better source now that one can be
built.

## Not client concerns

Submodule HTTP route registrations are ignored by the server itself (only the root
module's routes are used), and `HttpHandlers` / `HttpRoutes` remain unread by this SDK in
root and submodules alike.
